Overview

Airgent is a local-first personal agent runtime. One runtime is exposed through a CLI, a TUI, an HTTP API, and a WebUI.

The agent brain is the pi kernel (@earendil-works/pi-coding-agent). Airgent spawns one pi --mode rpc subprocess per session and speaks its JSONL protocol over stdin/stdout. pi owns model routing (15+ providers and OpenAI-compatible proxies), file & shell tools, skill discovery, and session trees. Airgent keeps short-term transcripts and long-term memory in a local SQLite store, persists pi conversations locally, and never touches your own ~/.pi.

Design stance

  • Local-first. Data lives in ~/.airgent/; SQLite with WAL; no cloud service in the loop.
  • Simple by default. With zero configuration Airgent is the thinnest useful wrapper around pi.
  • Power when asked. Sandbox, skill registry, MCP, sub-agents, guardrails, hooks, memory upgrades, and tracing are independent opt-in flags.

What's in the box

  • Four surfaces over one kernel: CLI, full-screen TUI, HTTP API, and a static WebUI.
  • A memory system with kinds, importance, decay, dedup, core blocks, and auto-extraction.
  • A cron scheduler that fires prompts through the same kernel.
  • An opt-in capability layer: sandbox, skills, MCP, sub-agents, guardrails, hooks, tracing.
Check what's enabled — run airgent status locally, or GET /api/v1/features over HTTP.

Quickstart

From clone to a running agent in three steps.

1 · Install the pi kernel (once)

curl -fsSL https://pi.dev/install.sh | sh
# or: npm install -g --ignore-scripts @earendil-works/pi-coding-agent

2 · Configure

uv sync
cp .env.example .env
# set OPENAI_API_KEY, optionally OPENAI_BASE_URL for a proxy

3 · Run

uv run airgent serve --reload    # API + WebUI on http://127.0.0.1:10304
uv run airgent chat "plan my day"
airgent tui

Global install

No manual virtualenv needed for normal use:

sh scripts/install.sh
airgent serve

First conversation

curl -X POST http://127.0.0.1:10304/api/v1/agent/run \
  -H 'Content-Type: application/json' \
  -d '{"input": "Summarize what the Airgent project does"}'

Open http://127.0.0.1:10304 for the WebUI. Sessions appear in airgent sessions list; memory in airgent memory list.

CLI

Airgent is driven by a Typer CLI. Every command works without the server running.

Chat

airgent chat "give me today's plan"   # one-shot
airgent chat                          # interactive; /exit, /new
airgent tui                           # full-screen TUI

Inside the TUI: Enter sends, / opens the command palette, /resume restores a session, Ctrl-O toggles execution detail.

Sessions

airgent sessions list
airgent sessions show <session-id>
airgent sessions delete <session-id>

Memory

airgent memory list
airgent memory search "uv python"
airgent memory add "Prefers uv" --tags python,tooling --kind preference --importance 0.9
airgent memory blocks
airgent memory set-block persona "Concise and blunt"
airgent memory delete-block persona

Cron

airgent cron create nightly-plan --input "Plan tomorrow" --schedule-kind cron --schedule-value "0 21 * * *"
airgent cron list
airgent cron trigger <job-id>
airgent cron pause / resume / delete <job-id>

Capabilities

airgent status                # config + enabled features
airgent sandbox               # effective sandbox provider
airgent skills list
airgent skills enable|disable <name>
airgent skills mode deny_all
airgent skills add-dir ~/more-skills

Sessions & cron

Sessions

Each Airgent session maps to one pi session file under ~/.airgent/pi/sessions (the binding is stored in SQLite, table kernel_sessions). Later runs resume the same pi conversation, preserving tool history and compaction. Airgent additionally mirrors user/assistant transcripts into its own database for listing and search.

Pass session_id in an API request (or --session on the CLI) to continue a conversation; omit it to start a new one and the id comes back in the response.

Cron

Scheduled prompts run through the same runner and land in the transcript as [CRON <name>] system entries.

  • schedule kinds: cron (5-field expression), interval (seconds), once (one-shot).
  • A background loop polls every 30s; airgent cron trigger fires immediately.
  • One-shots disable themselves after running.
§ capabilities / 01

Sandbox

Run the pi kernel subprocess inside a sandbox so every tool the agent executes — bash, file edits, extensions — inherits the confinement. Off by default.

export AIRGENT_SANDBOX=seatbelt   # macOS
# or
export AIRGENT_SANDBOX=docker     # any host with Docker
airgent sandbox                   # print the effective provider

seatbelt (macOS, recommended)

Airgent renders a sandbox-exec profile to ~/.airgent/pi/agent/sandbox.sb and launches pi behind /usr/bin/sandbox-exec -f.

  • Deny-by-default; system paths remain readable.
  • Writes confined to the workspace, ~/.airgent, /private/tmp, and /private/var/folders.
  • Network denied unless AIRGENT_SANDBOX_NETWORK=1.

docker (experimental)

The kernel runs as docker run --rm -i with the workspace and ~/.airgent bind-mounted at their host paths, --network none by default, plus a whitelist of environment variables.

FROM node:20-bookworm-slim
RUN apt-get update && apt-get install -y --no-install-recommends python3 \
    && rm -rf /var/lib/apt/lists/*
RUN npm install -g --ignore-scripts @earendil-works/pi-coding-agent
Image requirements — Node.js, a global pi install, and Python 3 (for the memory extension CLI). The container also needs the Airgent package importable; mount or bake the repo in.
§ capabilities / 02

Skills

pi discovers skills natively: .agents/skills/ in the workspace and ~/.agents/skills/ for user skills, scanned recursively for SKILL.md (the Agent Skills format). Only name and description enter the system prompt; the body is read on demand.

Skill registry (opt-in)

Set AIRGENT_SKILLS_REGISTRY=1 to add per-skill kill switches on top of native discovery:

airgent skills list
airgent skills disable brave-search
airgent skills enable brave-search
airgent skills mode deny_all      # default-deny; enable only what you list
airgent skills add-dir ~/more-skills
  • State lives in ~/.airgent/skills.json (mode / enabled / disabled / extra_dirs).
  • When the registry is enabled and something is actually filtered, Airgent writes a skills whitelist into the isolated agent dir's settings.json — your own ~/.pi is never touched.
  • Same control over HTTP: GET /api/v1/skills, POST /api/v1/skills/{name}/enable|disable.
Not a security boundary — the registry controls which skills load. Use the sandbox and guardrails for hard isolation.
§ capabilities / 03

MCP servers

pi intentionally ships without MCP; Airgent adds it. With AIRGENT_MCP=1, the airgent-mcp extension reads a Claude-Desktop-compatible config, spawns each stdio server, performs the JSON-RPC handshake, and registers every remote tool as a pi tool named mcp__<server>__<tool>.

Config

Defaults to ~/.airgent/mcp.json (override with AIRGENT_MCP_CONFIG). Airgent creates an empty template on first run:

{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/tmp"]
    }
  }
}

Notes

  • stdio servers only (command + args + optional env).
  • Tool schemas come from the server's tools/list; calls proxy through tools/call.
  • Startup timeout 15s per server; a failing server surfaces as an extension error, not a crash.
§ capabilities / 04

Sub-agents

With AIRGENT_SUBAGENTS=1 the kernel gains a spawn_subagent tool: the root agent delegates a self-contained subtask to a fresh headless pi --mode rpc --no-session process and receives its final answer.

spawn_subagent(
  task: "Audit tests/ for flaky patterns and list them",
  timeout_seconds: 300   # optional, 10–900
)

Behavior

  • Sub-agents see only the task text — put all needed context into it.
  • Depth-capped: children carry AIRGENT_SUBAGENT_DEPTH; the tool refuses beyond AIRGENT_SUBAGENTS_MAX_DEPTH (1–3), so delegation trees terminate.
  • Model defaults to your default model; override with AIRGENT_SUBAGENTS_MODEL.
Good fits — research sweeps, bulk refactors, well-scoped parallelizable work. Not for stateful edits that need this conversation's context.
§ capabilities / 05

Guardrails

With AIRGENT_GUARDRAILS=1, a policy file decides which tool calls are blocked before execution — enforced inside the kernel via the tool_call hook.

Config defaults to ~/.airgent/guardrails.json (override with AIRGENT_GUARDRAILS_CONFIG). Airgent writes a sensible default on first run:

{
  "denied_tools": [],
  "denied_commands": ["rm\\s+-rf\\s+/", "sudo\\s"],
  "denied_paths": ["(^|/)\\.env$", "secrets/"],
  "max_bash_timeout": 300,
  "message": "Blocked by Airgent guardrails policy"
}
  • denied_commands — regexes matched against bash commands.
  • denied_paths — regexes matched against read/write/edit paths.
  • denied_tools — tool names blocked outright.
  • max_bash_timeout — seconds; 0 disables the check.

Blocked calls return the policy message to the model as the tool error, so it can adapt instead of crashing.

§ capabilities / 06

Permissions & rewind

Permission tiers

Tiered tool permissions, off by default. Enable with AIRGENT_PERMISSION_MODE:

ModeBehavior
off (default)No checks — the plain pi wrapper
read-onlywrite/edit/bash blocked outright (plan-mode style)
workspace-writeEdits confined to the workspace + ~/.airgent; dangerous bash commands ask first

Ask/deny command patterns live in ~/.airgent/permissions.json (empty lists = built-in patterns: sudo, rm -rf, git push, package installs, curl | sh ask; rm -rf /, mkfs deny).

How approval reaches you

  • TUI — the prompt appears in the execution log; press y to allow, n to deny.
  • WebUI — a confirm dialog; the answer POSTs to /api/v1/agent/permission.
  • Headless (one-shot CLI, cron, /agent/run) — auto-denied.
  • Timeout — unanswered prompts are denied after AIRGENT_PERMISSION_TIMEOUT seconds (default 600).
Approvals ride the kernel's own UI protocol — the permission extension calls pi's ctx.ui.confirm, which blocks the tool until a surface answers. No polling, no side channel.

Rewind (checkpoints)

Always on, built on the pi kernel's native fork. Rewinding forks the conversation at an earlier user message; the transcript mirror is rebuilt from the forked branch.

airgent sessions rewind <session-id>              # numbered picker
airgent sessions rewind <session-id> --entry-id <id>
# TUI: /rewind opens a searchable palette
curl -X POST .../api/v1/sessions/<id>/rewind -d '{"entry_id": "..."}'

Rewind restores the conversation; files already written by the agent are not reverted.

§ capabilities / 07

Hooks

Lifecycle hooks run external commands around agent turns. Off by default; config at ~/.airgent/hooks.json (override with AIRGENT_HOOKS_CONFIG).

{
  "hooks": {
    "before_run": [{ "command": "/path/to/check.sh", "timeout": 10 }],
    "after_run":  [{ "command": "/path/to/notify.sh", "timeout": 10 }]
  }
}

Conventions

  • Each hook receives the turn payload as JSON on stdin — {input, session_id, agent_key} before, plus output after.
  • exit 0 — allow / success.
  • exit 2 — (before_run only) veto the run; stdout becomes the reason.
  • Anything else — failure is logged but does not block.
#!/bin/sh
payload=$(cat)
case "$payload" in *'"rm -rf"'*) echo "destructive input"; exit 2;; esac
exit 0
§ capabilities / 08

Tracing

With AIRGENT_TRACING=1, every turn records trace events into SQLite (table trace_events):

  • turn_start — input, session, agent key
  • turn_end — output size
  • turn_error — kernel error text

Read them from the store:

uv run python -c "
from app.memory.store import LocalStore
from app.core.config import get_settings
store = LocalStore(get_settings().db_path)
for e in store.list_trace_events(limit=20):
    print(e['created_at'], e['kind'], e['session_id'])
"
§ memory / 01

Memory system

Long-term memory lives in the same SQLite database as transcripts. Two model-facing tools are always available to the agent (via the bundled airgent-memory extension): search_memory and remember_note. Relevant hits are also injected into prompts automatically as an <airgent-context> block.

Records

Every memory carries:

FieldMeaning
kindfact | preference | profile | project | event
importance0.0–1.0 weight used by ranked search
tagsFree-form, lower-cased
access_count / last_accessed_atRetrieval bookkeeping (feeds decay)
airgent memory add "Ships on macOS arm64" --kind fact --importance 0.7

Search

Keyword hits are ranked by hits × (0.5 + importance), optionally multiplied by a decay factor (see Decay & dedup). Retrieval touches the record so hot memories stay hot.

Upgrade flags

FlagEffect
AIRGENT_MEMORY_DEDUP=1Near-duplicates are merged (token Jaccard ≥ 0.8)
AIRGENT_MEMORY_DECAY_DAYS=NImportance halves every N days without access
AIRGENT_MEMORY_CORE_BLOCKS=1Always-in-context blocks
AIRGENT_MEMORY_AUTO_EXTRACT=1Mine durable facts from user messages
§ memory / 02

Core blocks

Core memory blocks (Letta-style) are small named notes that are always in context. With AIRGENT_MEMORY_CORE_BLOCKS=1, every block is injected at the top of each prompt as <core-memory><key>…</key>…</core-memory>.

airgent memory set-block persona "Concise, blunt, code-first"
airgent memory set-block goals "Ship the Airgent v0.2 docs"
airgent memory blocks
airgent memory delete-block goals

HTTP equivalents: GET/PUT/DELETE /api/v1/memories/blocks.

Keep them small — blocks are paid on every turn. Persona, current goals, and hard constraints are the classic uses.
§ memory / 03

Auto-extract

With AIRGENT_MEMORY_AUTO_EXTRACT=1, every user message is mined for durable facts before the run — mem0-style extraction with a deterministic multilingual pattern matcher, so it needs no extra model calls.

PatternKindImportance
"记住…", "remember that…"fact0.8
"我叫…", "my name is…"profile0.9
"我喜欢…", "I prefer…"preference0.7
"我正在开发…", "I'm working on…"project0.6

Extracted facts are stored with the session as source and take part in ranked search immediately. At most five per message; duplicates are filtered within the message and (with dedup on) across the store.

§ memory / 04

Decay & dedup

Time decay (Zep-flavored)

Set AIRGENT_MEMORY_DECAY_DAYS=N and a memory's effective weight halves for every N days since it was last accessed (last_accessed_at, falling back to updated_at / created_at):

score = hits × (0.5 + importance) × 0.5 ^ (idle_days / N)

Searches touch what they return, so actively used memories never decay away. 0 (default) disables decay entirely.

Dedup

With AIRGENT_MEMORY_DEDUP=1, add_memory checks the store for an exact or near-duplicate (token Jaccard ≥ 0.8). On a hit it merges tags, bumps importance to the max, and refreshes the existing record instead of inserting a second copy — the memory id you get back is the original's.

§ reference / 02

Architecture

Kernel layer (app/kernel/) — one pi --mode rpc subprocess per session; process.py owns the JSONL protocol, events.py normalizes pi records into typed events, manager.py pools processes and resumes sessions, and setup.py materializes the isolated agent dir (~/.airgent/pi/agent: models.json, settings.json skills overlay, APPEND_SYSTEM.md, extensions) plus the sandbox launch spec.

Capability layer — app/sandbox/ (seatbelt/docker prefixes), app/skills/ (registry → pi settings.json whitelist), and three opt-in kernel extensions in pi/: airgent-guardrails.ts (tool_call policy), airgent-subagent.ts (delegation), airgent-mcp.ts (MCP bridge). Lifecycle hooks live in app/hooks/.

Service layer — app/agents/runner.py translates kernel events into progress events, persists transcripts, injects core blocks and memory hits, runs hooks, extracts memories, and traces turns. app/memory/store.py is the single SQLite store (sessions, transcripts, memories, blocks, cron, traces, kernel bindings).

Surfaces — FastAPI (app/api/), Typer CLI, prompt-toolkit TUI, static WebUI — all over the same AgentRunnerService.

Full module map lives in the repo's docs/ARCHITECTURE.md and AGENTS.md.

FAQ

Does Airgent touch my ~/.pi?

No. pi state is isolated under ~/.airgent/pi/; your own configuration is never read or written.

What runs by default?

The plain pi wrapper: built-in tools, native skill discovery, memory tools. Every capability flag defaults to off — verify with airgent status.

Do I need the server for the CLI?

No. CLI commands spawn the kernel directly. The server only adds the HTTP API and WebUI.

Is the seatbelt sandbox enough?

It confines writes and (by default) network for the kernel process tree. For stronger isolation use the Docker provider, and review what you expose via mounts.

Where is my data?

Everything in ~/.airgent/: airgent.db (SQLite, WAL), pi sessions under pi/sessions, policy/config files at the data-dir root. Delete the directory to reset.

How do tests run?

uv run pytest — 56 tests, no external services needed.
